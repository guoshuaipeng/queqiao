# S004 — 协助方「提议一项改动」等待与结果人话

> 场景：鹊桥-场景 · 2026-11-06 Asia/Shanghai  
> 状态：**已通**（R041 四态人话 / R042 跟包，产品已验收）。文头于 2026-11-06 按产品评测回执回写，避免误排。  
> 约束：不碰 macOS 正式下载、HTTPS、完整远程桌面；不改中继协议字段；不另发明信任等级文案。

## 结论（选哪条断点）

三条闭环里，**亲友协助 / 客户支持在「连上之后」仍高频断在写操作等待态**：协助方点了「提议一项改动」后，不知道对方是不是正在看确认窗；对方超时与拒绝在协助端被说成同一句；成功后又像「只提了议、没做完」。  
同事运维同一条写路径也会碰到，但亲友/客户更吃人话。

不选「复制本次已确认改动」作本条：被控端回看已在 R007/R013；本条先修协助方主路径上正在发生的等待与结果。

## 用户 / 场景

- **用户**：亲友协助方、客户支持（去协助端；Windows Helper.UI 与 Avalonia HelperWindow）。
- **场景**：已连上对方电脑 → 点「提议一项改动」→ 对方本机弹出「对方想在这台电脑执行操作」→ 允许 / 拒绝 / 超时。
- **现状断点**（对照源码，2026-11-06）：
  1. 等待中：Windows 协助端状态是「执行 RunCommand …」（控制台词）；Avalonia 等待中没有明确「在等对方确认」的人话。
  2. 成功后：Avalonia 写「已提议一项改动」，听起来像还没执行完；实际是对方已允许并已执行。
  3. 超时：被控端已把 `Error` 设成「确认超时，未做任何改动」，但协助端凡 `DeniedByUser=true` 就改写成「已拒绝，未做任何改动」，**超时与拒绝分不清**。协助方无法判断该再催对方看一眼，还是对方明确拒绝了。

## 步骤（可开发需求）

1. **发出提议后、对方点允许/拒绝/超时前**  
   去协助端主状态改为人话：**「正在等对方在本机确认…」**  
   不要出现 `RunCommand`、tool 名、英文协议词。只读四个常用操作不要套这句。

2. **对方允许且执行成功**  
   主状态改为：**「对方已允许，改动已执行」**  
   不要再用「已提议一项改动」表示成功。

3. **对方点拒绝**  
   继续用已有原文：**「已拒绝，未做任何改动」**（`WriteConfirmCopy.DeniedMessage`）。

4. **对方超时未确认**  
   协助端必须显示：**「确认超时，未做任何改动」**（`WriteConfirmCopy.TimedOutMessage`）。  
   实现注意：被控端已经把该句放进 `ToolResponse.Error`；协助端在 `DeniedByUser` 时**优先展示 `Error`（若非空）**，不要无条件盖成 `DeniedMessage`。本轮**不新增**中继/协议字段。

5. **范围**  
   Windows `Helper.UI` 与 Avalonia `HelperWindow` 都要改到；共用文案常量，便于锁测。  
   不改被控端确认窗原文、不改信任等级、不改五键显隐与顺序、不改官网包、不开实现轮以外的功能。

## 验收

1. 点「提议一项改动」后、对方尚未操作前：协助端主状态可见「正在等对方在本机确认…」，截图无 `RunCommand`。
2. 对方点「允许」且执行成功：主状态为「对方已允许，改动已执行」，不是「已提议一项改动」。
3. 对方点「拒绝」：主状态为「已拒绝，未做任何改动」。
4. 对方一直不点直到超时：主状态为「确认超时，未做任何改动」，**不得**写成「已拒绝，未做任何改动」。
5. Windows 与 Avalonia 去协助端均满足以上 1–4；只读操作（查看正在运行的程序等）成功态不必改成等待句。
