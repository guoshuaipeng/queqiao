> **本文是架构正式评估收口（2026-11-06 Asia/Shanghai）；不是实现授权；验证完成前不宣称现网已满足严格唯一凭证。**

## 0. 产品拍板（2026-11-06 10:35 Asia/Shanghai）

用户已明确选择 **严格唯一凭证**：

- 唯一连接凭证 = **会话 code + 8 位密码**
- **取消**：账号 / 同 owner 服务器声明免密、设备密钥快捷连接等旁路
- **自有设备也输入 code+密码**（不另设设备密钥快捷连）
- 继续以成熟 PAKE 为正式目标评估：服务器不知密码；恶意中继可测；重放 / 端点限速 / 密码生命周期；密码不得明文或可逆回传中继；code 中继可见，不承诺隐藏
- 与本机三档写确认正交
- **新方案运行验证（含恶意中继测试）完成前，不得宣称现有实现已安全满足该目标**

S1（密封指纹 + 默认官方中继诚实）仅作过渡 / 对照，**最终目标**是本文件的严格唯一凭证，而非长期停留在 S1。

## 1. 要兑现的承诺及边界

目标：会话 code + 8 位密码是远程控制的唯一会话秘密凭证；公网服务器不接收明文密码或可逆等价物，不因其 owner 声明/账号 token 授权控制。中继只路由、不见业务内容、不持有业务 TLS/端到端 PAKE 密钥。

**code 是中继可见的路由标识，不是对中继保密的第二因子。**“必须持有两者”指完整凭证定位会话并通过密码认证，不得把公开 code 的熵算进抵抗恶意中继的密码熵。此凭证认证的是有权协助的会话持有者，不证明人名、实名或机器永久身份。端点恶意、剪贴板泄漏、用户分享给错人及密码实际泄漏不在密码协议防护内。

身份认证与本机三档写确认正交：身份成功只是后续权限判断的必要前置，不自动提升档位、不自动同意写操作、不绕过本机确认。

## 2. 协议候选与现成实现

禁止自造 PAKE、椭圆曲线算术或把 HASH(pwd)/MAC 裸挑战应答冒充 PAKE。成熟协议不等于所有同名实现都经过审计；必须核验确切版本、测试向量、维护、许可证、恒时实现和 Windows/Net48/.NET8/Linux 绑定。

| 候选 | 角色与适合性 | 集成/实现评估 |
| --- | --- | --- |
| SPAKE2+，RFC 9383 | 协助端 Prover、Agent Verifier；临时会话在 Agent 本地建立 verifier，公网中继不持有 verifier。适合短时配对 | 可评估 Matter connectedhomeip 的 SPAKE2+ 实现适配；Matter profile 与 RFC 9383 密钥日程可能不同，不能直接互通。须锁定 profile 与对应向量；不是宣称现有 .NET 库即可用 |
| OPAQUE，RFC 9807 | aPAKE，支持密码隐藏和相互认证；Agent 是协议 server，协助端是 client；公网 relay 不是 OPAQUE server | 可评估 opaque-ke（Rust）或 bytemare/opaque（Go）；需核对版本是否实现 RFC 9807。bytemare 自述未独立审计；未据项目名承诺可直接生产。登记、OPRF/记录生命周期及跨语言绑定增加工程量 |
| CPace | 两端暂持同一会话密码的 balanced PAKE，模型贴近一次性配对 | 草案/profile 必须锁定；bytemare/cpace 自述概念验证和无保证，不能直接作为生产首选；需完整双向 key confirmation 的应用 profile |

推荐先做 Agent 终止的 SPAKE2+ 技术可行性验证，并对 OPAQUE 做备选评审；最终选型以可审计实现/跨平台可用性为门槛，不因 UX 排期自写替代。CPace 保留比较，不把草案和概念验证包装为成熟生产实现。

OPAQUE 的“server”指 PAKE 协议参与端，不等于公网服务器。若让公网中继担任 OPAQUE server，则该服务器持有认证状态和会话密钥，不能仅靠“OPAQUE 隐藏密码”推出它不能冒充 Agent；其完整凭证文件/OPRF 状态泄漏仍可支持离线字典攻击。本文首选公网只路由，认证 server 在被控端。

OPAQUE 登记需要已认证且保密的通道，不能通过未经认证的恶意中继首次登记并偷换身份。临时会话可在 Agent 本地通过成熟库完成一致的初始化，得到同一 password 的记录及 Agent 密钥状态；该本地登记方式和角色分配必须做协议专家评审。SPAKE2+ verifier 同样仅本地生成；不将 verifier/OPRF seed/私钥交给中继。

## 3. 与现有业务 TLS / fp 的关系

1. Agent 本地生成会话密码、全新会话 epoch/实例和临时业务证书；中继仅分配/映射公开 code。会话密码不经 guest_host/guest_join 发给公网中继，亦不放 URL/可逆密文供其解密，不发可离线验猜的简化 hash 验证字段。
2. 协助端以 code 请求未认证路由；中继可以转发、乱序、丢弃、替换，但不能宣布“已授权控制”。在认证前 Agent 仅开放有严格帧长/超时/并发限制的握手状态机，绝不开放业务命令解析。
3. 协助↔Agent 执行完整 PAKE，按标准验证群元素和双方密钥确认。context 规范化绑定产品域、角色、协议/profile、code、Agent epoch、双方新鲜随机数及能力/版本；不能仅由中继未验证声明决定。code 必须作为认证 context，使只持密码但使用错误 code 的会话失败。
4. 在 PAKE 完成并确认后，从标准输出密钥按分域 KDF 派生认证封装密钥，在认证信道传送 Agent fp、epoch、有效期及完整 transcript 绑定；不得使用原始 8 位密码直接加密 fp 当 PAKE 替代。随后创建并验证以该 Agent fp 钉扎的端到端业务 TLS。
5. 所有业务数据在 Agent TLS 建立且双方 PAKE 状态有效后才能处理；Agent 还须将控制授权绑定到**同一** TLS 会话，不能因为某个并行连接做过 PAKE 就放行另一连接。应以经过评审的 TLS exporter/应用双向确认机制绑定该 TLS、PAKE transcript 和角色；运行时是否支持 exporter、替代方案的组合证明是落地前置，不能以“已传 fp”替代授权绑定。
6. 如采用 TLS-PSK 等替代集成，须确认现有两端运行时支持并形成独立安全评审；不能为了集成便利先建立跳过验证的业务 TLS 再称其为已认证。PAKE 前路由是受限认证引导管道，不是可处理业务的明文降级通道。

## 4. 主动恶意中继：可证明的成功/失败边界

在两端实现正确、秘密未泄露、使用足够随机临时量、绑定完整、端点限速有效条件下，中继仅知道 code 和协议 transcript 不应离线恢复密码或伪造一次成功的端到端认证，也不能替换 fp、把自己证书变成 Agent。

中继能阻断/拖延/枚举路由、观察连接元数据；可作在线猜测或冒充端点尝试，对两端均须限速。PAKE 不提供可用性保证，也不承诺 8 位密码永远猜不中。如果中继从旧 guest_join、日志、S1 兼容回落或用户泄露获 pwd，则已突破威胁模型；它可作为凭证持有人参加 PAKE。因此新模式必须完全不向它发送 pwd，且不复用曾暴露的旧密码。

单纯完整转发使真正两端认证成功，是允许的；这不代表中继获得控制/读取业务的能力。跨会话交换、角色反射、伪造成功、换证书或改能力必须失败。

## 5. 重放、跨会话与降级

PAKE 每次使用库要求的新鲜临时量，双方 nonce 和 Agent 新 epoch；不得重用握手密钥。短 code 可循环分配，但新实例不可等于旧实例。认证 transcript 和 TLS 授权确认绑定 code/epoch/角色/profile/能力；旧确认、旧 fp 封装、旧 TLS/旧密码不可迁移到新 epoch。

Agent 在认证成功后原子消费会话或将其绑定到唯一允许连接；并行 join 不能双重授权，失败 join 不应让攻击者永久夺走会话。重连需要新的 PAKE/确认或经单独评审的绑定恢复机制，不能仅凭服务器发的 session token。禁止 TLS 0-RTT 执行控制命令及重放授权。

客户端唯一凭证模式不回退 S1/旧 guest_* 明文密码。版本不支持时停止，不能以“兼容”为由重发 pwd。升级到新模式重新生成密码和 epoch，并阻断旧 S1 等待态；不可把同一密码同时登记两套模式。

## 6. 8 位密码限速、重置和生命周期

8 位十进制上限约 26.6 bit，8 位 32 字符集约 40 bit，且须 CSPRNG 均匀抽样；密码长度不等于强密码。UI 字符集和规范化须固定并体现在 profile，不允许用户复用弱口令。

最终防线必须在 Agent 和协助端，不只 relay；恶意 relay 可以移除自身限制或换 IP。建议评审基线：每个 Agent epoch 最多 5 次未成功认证尝试、串行或极小并发、指数退避，超额使本地会话失效并要求本机新建；协助端对同一凭证遇连续服务器认证失败停止自动重试。具体阈值需可用性/DoS 联合验收，不是已经发布参数。

开始提供可供对方验猜的响应即计入尝试预算；不能只统计最终显式“密码错误”，缺少 KE3/确认、超时、断连均按失败计数，防止恶意对方不发最终消息绕过预算。预算绑定本地 epoch，不信任中继重连/改 code 来重置。

短时等待 TTL、一次性使用、会话关闭、Agent 重启、主动换码或密码重置均清除密码、verifier/OPRF 临时状态和密钥，并生成新密码/epoch；计时采用本机可信单调时间而非中继可任意延长的字段。旧 session 不因 relay 数据残留复活。重置必须由本机明确授权或已验证的既有端点授权机制发起，不能仅凭服务器 owner 声明。

## 7. 账号免密 / 设备密钥旁路：已取消（拍板）

严格唯一凭证模式下：

- **禁止**仅凭服务器 owner 声明 / 账号 token 授权连接或控制
- **禁止**本机登记协助设备公钥后的免密快捷连（用户明确：自有设备也输入 code+密码）
- 服务器账号若仍存在，仅可用于发现、计费、审计等**非授权**用途，不能单方新增控制权
- S0 完整载荷若保留为高级排障形态，须明确隔离：不得与「严格唯一凭证模式」同时宣传为唯一路径；实现上不得成为绕过 PAKE 的授权旁路
- 任何恢复 / 管理台能力不得重新引入服务器可单方换凭证或授权控制的后门

身份认证与本机三档写确认仍正交：本机可对本已授权会话按档位减免写确认，但不能用服务器声明跳过身份。

## 8. S1 vs PAKE 工作量与推进门槛

| 维度 | S1 过渡 | PAKE 唯一凭证 |
| --- | --- | --- |
| UX | 两行短凭证 | 同样两行短凭证 |
| 服务器密码 | 旧 join 可见，依赖运营方诚实 | 公网不接收，端点相互认证 |
| 协议范围 | host 封装登记/join 字段/客户端解封 | 新握手状态机、密码不出端点、TLS 授权绑定、端点限速/生命周期、旁路已拍板取消，实现须收口 |
| 安全依赖 | 官方中继诚实 | 标准 PAKE、端点、审计实现与正确组合 |
| 工作量量级 | 中等跨端协议改造，至少一个完整实现/安全回归轮次 | 大型多轮安全工程：选型/绑定 PoC、跨平台实现、恶意中继对抗、独立审查；通常数周级而非一天字段补丁；未核仓不作人日承诺 |

S1 可作为明确告知信任边界的过渡评估，不满足新目标；唯一凭证模式的发布必须等第 7 节已拍板取消旁路；另需协议 profile/库审计、旧路径隔离和以下测试闭环。本轮只 docs，不修改客户端/中继/生产。

## 9. 必须执行的恶意中继测试（未执行）

测试用可控中继替换官方服务；控制其中继进程、消息、日志和数据库，而不是仅验证正常连通。正向确保两端可在不额外 OOB fp 情况下通过 PAKE 和 Agent TLS，业务仍端到端加密。

- 抓取 guest_host/join、持久化和所有日志，确认无 pwd/可逆载荷/可离线验猜简化验证器、业务 fp/完整 PairQrPayload；仅由端点持有 PAKE/业务密钥。
- 中继替换自身 fp/证书、改 PAKE 公钥/确认、宣称 owner、伪造 join 成功：两端不能执行任何业务操作。
- 截取重放、双连接拼接、反射、跨 code/跨 epoch、证书轮换、并行 join、旧封装、旧账号 token：绑定不一致必须失败。
- 剥离版本/能力、返回“旧中继”、触发 S1 回落：新模式停止，网络上始终不出现 pwd。
- 中继无限重连/换 IP/改 code/并行分发/不发最终确认：端点总预算仍生效，无无限猜测 oracle；客户端也不被驱动无限响应。
- 重置/重启/到期/结束后旧凭证、恢复 token 与旧 PAKE 状态失败；管理台无法直接授权控制。
- 两端握手前/中/后本机三档写确认保持原有边界；身份失败时任何档均不执行写入。

测试是可证伪的验收证据，不是密码学证明；还需标准测试向量、模糊测试、实现审计及组合协议审查。

### 11.1 选型建议（推荐 / 备选 / 不包装为首选）

| 优先级 | 协议 | 架构建议 | 理由 |
| --- | --- | --- | --- |
| **首选推进** | **SPAKE2+（RFC 9383）**，**Agent 终止**（Agent=Verifier，协助=Prover） | 先做技术可行性路径 / PoC | 临时会话在 Agent 本地建 verifier，公网中继不持有 verifier；模型贴近一次性配对；RFC 成熟。须锁定 profile（勿与 Matter 日程混用）与测试向量；跨语言以可审计实现为准，**不**因 UX 排期自写曲线算术 |
| **备选** | **OPAQUE（RFC 9807）**，Agent 作协议 server、协助作 client；**公网 relay 不是 OPAQUE server** | 备选评审 | aPAKE、密码隐藏与相互认证更强；登记/OPRF/记录生命周期与跨语言绑定工程量更大；库须核 RFC 9807 版本与审计状态。若误让公网中继当 OPAQUE server，则服务器持认证状态，**不能**仅靠「隐藏密码」推出不可冒充 Agent |
| **不包装成生产首选** | **CPace** | 仅作比较 | 草案/profile 须锁定；公开概念验证实现自述无保证，**不得**写成成熟生产首选 |

**结论（架构）**：推荐**先做 Agent 终止 SPAKE2+ 可行性路径**；并行保留 OPAQUE 备选评审门槛（审计、Net48/.NET8/Linux 绑定、登记通道）；CPace 不作为生产首选包装。最终库/版本以可审计实现与跨平台可用性为门槛，本文不点名「已可用生产库」。

### 11.2 集成边界（Net48 / .NET8 / Linux · TLS · 中继）

1. **客户端形态**
   - **Windows 亲友主路径**：**Net48**（`src-net48`）。任何原生库须可在 .NET Framework 4.8 进程加载，或经已评审的进程外 helper；禁止默认要求用户另装未说明的运行时。
   - **Mac / Linux / Avalonia**：**.NET 8**（`src`）。可用 P/Invoke / 官方扩展；打包须进现有自包含/依赖框架策略，体积与签名门槛按 `architecture.md` 平台轨道。
   - **Linux FFI**：若走 Rust/C 实现，须固定 ABI、提供 linux-x64（及后续目标）产物、可复现构建与许可证审查；禁止「开发机有 .so、用户机没有」的隐式依赖。
2. **TLS / 会话绑定**
   - PAKE 完成并密钥确认后，经分域 KDF 在**认证信道**传递/确认 Agent `fp`、epoch、有效期与 transcript 绑定；**禁止**用原始 8 位密码直接加密 fp 冒充 PAKE。
   - 业务 TLS 仍钉扎**该次 Agent fp**；控制授权须绑定**同一** TLS 会话。优先评估 **TLS exporter**（或经独立安全评审的应用层双向确认）绑定 TLS ↔ PAKE transcript ↔ 角色。运行时若缺 exporter，须先有替代组合证明，**不能**以「已传 fp」替代授权绑定。
   - 禁止：先建立跳过验证的业务 TLS 再称已认证；PAKE 前路由仅为受限握手管道，不解析业务命令。
3. **与中继 JSONL 的关系**
   - 中继继续：分配/映射公开 `code`、转发受限握手字节、配对后透明 pipe；**不知明文密码**、不持有 PAKE/业务 TLS 密钥、不宣布「已授权控制」。
   - `guest_host` / `guest_join`（及后续草案扩展）**不得**再提交明文 `password`、可逆密文或可离线验猜的简化验证字段作为授权依据。
   - 今日现网仍可能经 `guest_*` 见明文密码——属遗留，**不是**严格唯一凭证已兑现。S2 上线后旧明文路径须隔离/停止，禁止兼容回落泄密。

### 11.3 `guest_*` / 协议扩展草案（方向 · 非已部署）

> **草案**。线格式、字段名、错误码须在实现授权后写入 `relay-protocol.md` 并经评审；本节只定方向。

**能力协商（概念）**

- 双方在控制面声明 `cred_mode` / `pake_suite`（例：`spake2plus-rfc9383-v1`）；中继只透传，不解释为授权。
- 任一方或中继缺能力 / 被剥离能力 → **停止**；**不**发送 pwd 探测；**不**回落 S1/旧明文 `guest_join`。

**登记 / 等待（Agent 侧，概念）**

- Agent 本地生成会话密码、epoch、临时业务证书与 SPAKE2+ verifier（或 OPAQUE 本地记录）；中继仅得公开 `code` 与「短路径 ready」类状态位（不含 pwd/verifier 密钥材料）。
- 可选：host 连接内登记「PAKE ready」元数据（实例 id、suite、过期），**禁止**登记明文 pwd / verifier 私钥 / OPRF seed。

**Join / 握手（概念）**

- 协助端以 `code` 取得受限路由后，在 pipe 或控制面扩展帧上跑完整 PAKE；双方校验群元素与密钥确认。
- context 至少绑定：产品域、角色、suite/profile、`code`、Agent epoch、双方 nonce、能力/版本。

**错误码方向（草案名，可改）**

| 方向 | 含义 |
| --- | --- |
| `pake_required` | 对端/本模式要求 PAKE，当前能力不足 |
| `pake_suite_unsupported` | suite/profile 不识别或被降级 |
| `pake_verify_failed` | 密钥确认/群元素/上下文失败（对用户可归并为「验证失败」） |
| `pake_budget_exceeded` | 端点尝试预算用尽，须本机新建会话 |
| `pake_epoch_mismatch` / `pake_stale` | 跨会话/过期/已消费 |
| `pake_relay_downgrade` | 疑似剥离能力或诱导旧路径 |

中继可继续返回路由类错误（`invalid code`、过期、peer offline）；**不得**用「password ok」类语义代替端点 PAKE。

### 11.4 旁路收口清单（待实现轮删除或隔离）

严格唯一凭证模式下须收口（产品已拍板取消旁路；现网若仍存在则属遗留）：

| 项 | 动作方向 |
| --- | --- |
| `ownerLink` / 同 owner 服务器声明授权控制 | **删除或硬隔离**；不得作为连接/控制授权 |
| `connect_device` 免输会话密码 | **删除或硬隔离**；列表发现若保留则不可单方授权控制 |
| 设备密钥 / 本机登记协助公钥免密快捷连 | **删除**；自有设备也须 code+密码 |
| 账号 token 仅凭服务器声明授权控制 | **禁止**；账号若保留仅限发现/计费/审计等非授权用途 |
| 旧 `guest_join` 明文 password | S2 模式下 **停止发送**；兼容探测禁止泄密 |
| S0 完整 `remoteassist:pair` | 可保留为**高级/排障**独立根信任，须与「严格唯一凭证主路径」宣传隔离；**不得**成为绕过 PAKE 的静默授权旁路 |
| 管理台 / 恢复能力 | **不得**提供服务器单方换凭证或授权控制的后门 |

身份认证成功 ≠ 抬高写确认档位；三档写确认正交不变。

### 11.5 恶意中继测试（必须执行 · 当前：**未执行**）

状态：**未执行**。下列为发布前必须跑完的清单与通过门槛（可证伪验收，非密码学证明）。

**环境**：可控恶意中继（控进程、消息、日志、DB），非仅官方中继连通性测试。

**必须用例（摘要，细节见 §9）**

1. 抓取 host/join、持久化、日志：无 pwd / 可逆载荷 / 可离线验猜简化验证器 / 业务 fp / 完整 PairQrPayload；PAKE/业务密钥仅端点持有。
2. 替换中继自身 fp/证书、篡改 PAKE 消息/确认、伪造 owner、伪造成功 join：两端**零**业务操作。
3. 重放、双连接拼接、反射、跨 code/epoch、证书轮换、并行 join、旧封装、旧账号 token：绑定失败。
4. 剥离能力、宣称「旧中继」、诱导 S1/明文回落：新模式停止；线上始终无 pwd。
5. 无限重连/换 IP/改 code/扣最终确认：端点总预算仍生效；无无限猜测 oracle。
6. 重置/重启/到期后旧凭证与恢复 token 失败；管理台无法直接授权控制。
7. 握手前/中/后本机三档写确认边界保持；身份失败时任何档不执行写入。

**通过门槛**

- 上述用例全部记录证据（日志红线检查 + 两端行为断言）；任一项失败不得标安全 PASS。
- 另附：标准测试向量、基础模糊、实现/组合协议审查记录（可外审）。
- **编译通过 / 文档核对 ≠ 本清单通过。**

### 11.6 剩余风险（收口时仍开放）

- 8 位密码熵有限：依赖端点限速与生命周期；不承诺「永远猜不中」。
- TLS exporter 在 Net48 / 目标运行时的可用性未实测；替代绑定需独立评审。
- SPAKE2+ / OPAQUE 具体库的审计级别、许可证、恒时与 Windows/Linux 绑定未锁定 release。
- Matter 等异 profile 误用导致「能跑但不互通/弱绑定」的工程风险。
- 端点恶意、剪贴板泄漏、用户把码发给错人：协议外。
- 中继 DoS / 拖延：无可用性保证。
- 遗留旁路若实现轮未删净，唯一凭证宣传不成立。
- Linux/Avalonia 与 Net48 行为漂移（见 `backlog-linux-credential-align.md` 待查重）可能造成「一侧以为已 S2、一侧仍明文」——属发布前兼容矩阵风险。

### 11.7 产品对照验收建议条目（供产品写验收）

实现授权后，产品验收建议至少覆盖：

1. **唯一凭证 UX**：主路径仅 code+8 位密码可连；自有设备亦须输入；无设备密钥/免密入口宣传与可达路径。
2. **中继不见密**：恶意/官方中继抓包与 DB 无明文 pwd、无业务 fp 明文用于冒充；管理台/审计无 pwd/完整载荷。
3. **旁路已收口**：`ownerLink` / `connect_device` 免密 / 设备密钥快捷连不可完成控制授权（删除或明确隔离且测试证明不可达）。
4. **恶意中继清单 §11.5**：全部执行并附证据；失败不得 PASS。
5. **无危险回落**：能力剥离或旧中继时停止；网络无 pwd；不 TOFU、不自动 skipTls。
6. **TLS 绑定**：业务命令仅在「PAKE 成功且同一 TLS 会话绑定」后受理；换连接/换证书失败。
7. **写确认正交**：三档行为与身份结果解耦；身份失败不写。
8. **平台分标**：Net48 与 Linux/Avalonia **分别**验收；Linux PASS ≠ Net48 PASS。
9. **部署状态**：按 `architecture.md` 部署三态区分本机实现与公网已验；未部署 ≠ 功能坏。

### 11.8 S1 vs S2：过渡建议（利弊 · 节奏交产品拍板）

> **架构不擅自将节奏标为已决。** 下列供产品选择推进顺序。

**方案甲 — 直冲 S2（PAKE 唯一凭证）**

- *利*：一次对齐用户拍板的严格唯一凭证与「服务器不知密码」；避免 S1 上线后再撕掉密封路径；减少「短码已可连」在 S1 信任边界下的误宣传窗口。
- *弊*：工程与安全验证量大（选型 PoC、跨平台、恶意中继、旁路收口）；亲友短码体验上线更晚；期间主路径仍须完整载荷（含 `fp=`）或接受不可用短码。

**方案乙 — 先 S1（密封指纹 + 默认官方中继诚实）再 S2**

- *利*：可较快兑现「两行短码」UX（在**明示**信任官方中继的前提下）；协议改动相对 PAKE 较小；可为 S2 留出库/FFI 时间。
- *弊*：**不**满足「服务器不知密码 / 抗恶意中继」；已获 pwd 的中继可重封 fp；若宣传成最终目标会与拍板冲突；S1→S2 仍要做旁路收口与防回落，总工作未必更少；存在「临时方案永久化」风险。

**架构倾向（非产品已决）**：若产品愿接受短码体验继续延后，**倾向直冲 S2**，S1 仅作文档对照与威胁模型基线；若产品必须先上短码 UX 且接受书面信任边界，可授权 **明确标为过渡** 的 S1，并同时排期 S2，禁止把 S1 写成最终唯一凭证。
